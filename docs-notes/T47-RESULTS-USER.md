### Where the 1.2 s to a confirmed stop goes (2026-11-27)

"Confirmed stopped" (3.2.2f, 1,201.1 ms) is measured from the start of the lock request (`kill-switch.ts`) and covers three things in turn: writing the lockdown into `policy.json` (before the signal, on purpose: lock first, then abort), the signal (13.5 ms), and waiting until the dashboard prompt leaves the run table, which happens only after the runner's `agentCommandFromIngress` returns **and** `closeStoppedGovernanceTurn` has written the closing note into the session transcript (`governance-agent-runner.ts`). The Gateway journal for the 3.2.2f lock (`journalctl --user -u openclaw-gateway -o short-precise`) shows `22:05:19.020` "embedded run failover decision … surface_error" (the run reacting to the stop) and `22:05:19.432` "run … ended with stopReason=aborted": **412 ms for the run to return**. The policy write and the closing note have no log lines, so their share is not known (idle lockdown 11-23: 171 ms in total).

Not a function of how long the prompt has run: the signal is constant (13.5 ms mid-run, 1.4 ms idle), the policy write is the same file each time, and the winding down depends on what is in flight at that instant. The closing note searches the session transcript for its newest message first, so it may grow with the **conversation's** length (not measured).

### Fix for the streaming stall (2026-11-26, UNCOMMITTED, not yet on the VPS)

At Mohammad's word ("fix them and make sure that the emergency kill switch activates in less than 1 second"). Four changes, each with a test that fails without it:

1. **The event loop gets a turn during a burst** (the part that bounds the kill switch's wait). New `src/agents/embedded-agent-subscribe.event-slice.ts`; `embedded-agent-subscribe.handlers.ts` `scheduleEvent` runs each streamed-event handler through it: once one run's burst has handled more than 64 events (`EVENT_SLICE_MIN_EVENTS`) **and** held the main thread for 25 ms (`EVENT_SLICE_MS`) in one turn of the event loop, the next handler waits for a `setImmediate`, so pending HTTP requests (the kill switch, Cancel, `/healthz`) are accepted before the burst carries on. One tracker per subscription. Handlers keep their order. An ordinary trickle of events never yields, so delivery stays synchronous where it was (a first version with one shared 25 ms budget and no event minimum deferred handlers in 96 existing synchronous tests, which run many tests in one turn; caught by the subscribe suite and replaced). Test `embedded-agent-subscribe.event-slice.test.ts`: a 300-chunk burst costing 600 ms through the real subscription dispatcher; work queued before it runs after one slice (fails without the fix: 643 ms, after the whole burst), and every chunk still arrives, in order. 3. **Session observer remembers "no utility model" for a second** (`src/gateway/session-observer.ts`): a run whose agent has no utility model is never admitted and was re-claimed, and the model re-resolved, on every event; that one answer is now reused for at most 1 s under the same configuration object.
