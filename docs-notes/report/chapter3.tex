\chapter{System Design}
\label{ch:design}


The preceding chapter established that OS-level Agents introduce a
kind of vulnerability that is cognitive, and not deterministic, and that what
an attacker often manipulates is the reasoning of the agent itself. Any control that is
built inside the model, or that relies on the model's own judgment to enforce
it, therefore inherits the weakness it is meant to correct. The design in this chapter, briefly described in previous sections, begins from the
assumption that the agent is untrusted, and places a deterministic policy check
on the path that every tool call by an agent takes. This required that the
governance layer be built as a hard fork compiled into the OpenClaw core rather
than as a plugin installed alongside it. This commits the project to an entire upstream codebase, including native client
applications that this work does not modify.

On that foundation the layer adds five capabilities to the host: a default-deny
policy gate on the tool-call path, a tamper-evident audit ledger, an emergency kill-switch that measures the time to a confirmed stop, four tiers of named human accounts with individual sessions and levels of authority, and a management interface through which each of these is operated.
The chapter discusses requirements and the finished system.
Section~\ref{sec:gov-requirements} briefly restates the nine design requirements of
Section~1.3.
Section~\ref{sec:gov-reqanalysis} then analyzes them, describing the status the system has reached in relation to each one.
Section~\ref{sec:gov-constraints} does the same for the design constraints of
Section~1.4. Section~\ref{sec:gov-approaches} presents
the alternatives that were seriously considered and the reason each was
rejected, and Section~\ref{sec:gov-developed} describes the system as built, one
design area at a time, ending with what the system does not defend against; in other words, accepted limitations.
Where the developed design departs from the preliminary design of Chapter~1, the
departure is stated where it arises and the reason is given with it.

\section{Design Requirements}
\label{sec:gov-requirements}
As stated in Chapter 1, the design shall achieve the following requirements:

\begin{enumerate}
    \item The system shall be implemented using the Node.js runtime (version 18 or higher) and developed primarily in TypeScript with static type checking enabled.
    \item The system shall provide a secure web-based dashboard that enables administrators to configure customized privilege policies, monitor active autonomous agent sessions, and manage system operations using role-based access control.
    \item The system shall enforce a default-deny, policy-based security model that restricts autonomous agent access to operating system resources, including file system paths, process execution, and network communication, based on administrator-defined capabilities.
    \item The system shall support customized, fine-grained privileges for autonomous agents, including path-level file access, command allowlisting, network allowlisting, and time-limited permissions.
    \item The system shall continuously monitor autonomous agent activities and shall record 100\% of agent actions, policy decisions, and administrative approvals in an auditable logging system.
    \item The system shall implement tamper-evident audit logging mechanisms to ensure the integrity and traceability of all recorded agent and administrative actions.
    \item The system shall provide real-time administrative control capabilities, including the ability to suspend or terminate an autonomous agent session within a maximum response time of one second.
    \item The system shall prevent sensitive data (such as secrets or credentials) from being written in plaintext to log files.
    \item The system shall be deployable on a Linux-based operating system using open-source software components only.
\end{enumerate}

\section{Analysis of Design Requirements}
\label{sec:gov-reqanalysis}

This section explains how the design requirements shaped and influenced the developed system.
Each requirement is addressed by a component of the governance layer, including the
implementation technology, policy enforcement, auditability,
administrative control, credential protection, and deployment.

Requirement 1 specifies Node.js, TypeScript and static type checking. The system
was developed as a hard fork of OpenClaw using Node.js and TypeScript, with
strict type checking enabled across the core, user interface, and test code. This retains compatibility with the host framework and provides the type
checks required for security-sensitive policy and audit operations.

Requirement 2 requires a secure web-based dashboard with role-based access
control. The resulting Governance page allows authorized operators to configure
policies, manage agents and review active work through four account tiers: Root,
Administrator, User and Viewer. The dashboard communicates with the governance
HTTP control plane, while its permissions are checked against the authenticated
governance account before an administrative operation is completed.

Requirements 3 and 4 require a default-deny policy model and detailed,
customized privileges. Before an agent tool call reaches an operating-system
resource, which can exhaustively be a network address, a file path, or a terminal command, the governance layer evaluates the relevant resource. Rules can specify the resource, access
direction, effect and optional expiry time. This structure supports path-level
file permissions, command and network allowlists, and permissions that expire
when a temporary task no longer requires them. Building a robust RBAC system implied a multi-tenancy system alongside it, to allow different accounts on different devices on a single installation on a Linux VPS (as specified by Requirement 9). A version of this system was built.

Requirements 5 and 6 concern the audit ledger. Every agent tool invocation,
policy decision, and administrative approval is recorded in the tamper-evident governance ledger.
Where a call cannot be evaluated against a resource rule, its record identifies
that condition as \texttt{ungoverned}; it is not represented as an allowed
operation. There is a number of reasons why a call may not be governed. Table \ref{tab:gov-ungoverned} shows these tools and the reasons each is ungoverned. For example, the tools under 'Model-facing bookkeeping', 'Display surfaces', 'Content generation', and 'No hostname to match' in Table \ref{tab:gov-ungoverned} do not have a resource in their argument to govern. Each entry is bound to its predecessor using a keyed HMAC-SHA256 hash,
and an independent verifier can identify the first point at which a ledger has
been altered. The ledger therefore provides a complete account of activity and a
means of detecting modification.

Requirement 7 requires real-time administrative control over an agent session.
An authorized operator can place an agent in lockdown, after which new governed actions
are refused, and can request termination of work already in progress through the
Gateway's run-control mechanism. The policy change and abort request are applied
within the one-second requirement. Confirmation that work already in progress has
ended is reported separately, because its duration depends on the work being
terminated and the hardware capabilities of the host machine.

Requirement 8 prevents secrets and credentials from being recorded in plaintext.
The ledger uses the host framework's existing redaction component at the single
entry-writing boundary. Resource strings and recorded tool content are redacted
before they are hashed and appended, so the tamper-evident record contains the
sanitized representation. Reusing this component avoids introducing a second
redaction implementation while retaining coverage for the credential formats
already supported by the host framework.

Requirement 9 requires Linux deployment using open-source software components.
The governance layer adds no proprietary service or dependency and is built from
Node.js facilities and packages already used by OpenClaw. Deployment was validated
on an Ubuntu virtual private server purchased through Contabo, where the governance suite completed with
3,211 passing tests, 16 skipped tests and no failures across 197 files. The same
suite on Windows produced 3,206 passing tests and 21 skipped tests, giving the
same total of 3,227 tests across both platforms.

\section{Analysis of Design Constraints}
\label{sec:gov-constraints}

This section examines the economic, manufacturability, sustainability, ethical
and professional constraints that influenced the developed system, as described in Chapter \ref{ch:dsn-cs_1}. These
constraints determined the acceptable operating cost, deployment environment,
resource usage and scope of the governance layer.

The economic constraint limits the combined cost of model access and one year of
virtual private server rental to 350~JOD. Two VPS environments were purchased for the completion of this project: one for testing OpenClaw itself, and another for installing, developing, and running our fork of OpenClaw. Together, from March to September 2026, the cost was \$38.70, or 27.44~JOD. The projected cumulative price from October 2026 to January 2027, given the current monthly costs of both VPS installations, is \$55.80, or 39.56~JOD. The total VPS costs from March 2026 to January 2027 is therefore projected to be exactly 67~JOD. 
The LLM provider chosen was Kimi. The total costs associated with the Kimi subscription required to install and test the governance layer, calculated from monthly subscriptions from March 2026 to January 2027, is \$171, or 121.24~JOD. The total cost, combining both VPS and model costs, is 188.24~JOD, which is less than the 350~JOD maximum.

The manufacturability and sustainability constraint requires deployment on a
virtual private server with at least 8\,GB of RAM while maintaining stable and
manageable operation. The selected Contabo Cloud VPS 6 runs Linux and provides
12\,GB of RAM, six CPU cores, and 200\,GB of disk space. Its memory capacity
therefore exceeds the minimum requirement. The governance layer runs
inside OpenClaw's existing Gateway process, so it does not require a separate
server process or database service. Its in-memory login-throttle structure is
limited to 1,000 entries, and the audit ledger rotates into numbered archives at
8\,MiB to prevent unlimited growth of the active file. Deployment on this server
was validated by completing the governance test suite without failure.

The ethical and professional responsibility constraint limits the project to
defensive, governance and monitoring purposes. Policy enforcement can refuse an
agent action, require human approval or leave the decision to the security checks
already provided by the host framework. It does not widen the permissions
available to an agent. Administrative actions and agent activity are recorded in
the same tamper-evident ledger, sensitive values are redacted before storage, and
account roles restrict operators to the agents and functions assigned to them.
These controls support accountability, thereby supporting non-repudiation, privacy, thereby supporting confidentiality, and responsible administrative
oversight, thereby supporting authenticity.

One practical scope condition was also considered. Development was performed
primarily on Windows, while the intended deployment environment is Linux, so the
system was tested separately on the Ubuntu deployment host to account for
platform-specific behavior.
\section{Different Design Approaches}
\label{sec:gov-approaches}

Several
design decisions related to the requirements had more than one feasible approach, and the choices between
them affected the enforcement boundary and the reliability of the controls. This section compares the alternatives
that were considered. Each comparison identifies the available
approaches, the selected approach, and the reason for the selection. The
detailed operation of the selected mechanisms is presented in
Section~\ref{sec:gov-developed}.

\subsection{Gate Placement}
\label{sec:gov-gate-placement}

After it was decided that the system would be developed as a hard fork of OpenClaw and not as a plugin, the next decision concerned the
location of the policy gate. Adding checks separately to individual tools was
rejected because each tool would become responsible for applying the same
security rule, and a newly added or overlooked tool could bypass enforcement.
The host's central pre-execution policy function, \texttt{runBeforeToolCallHook}, was selected instead because
in-process tool calls enter it before their requested actions are performed.

Two positions were possible inside \texttt{runBeforeToolCallHook}. OpenClaw
already contained a short-circuit, an early return that ends the
function when none of the remaining policy stages need to run. An active plugin
hook is a \texttt{before\_tool\_call} callback registered by an enabled plugin
to inspect a tool call before execution. Other later policy sources include
trusted tool policies and tool-specific approval logic. If none of these
components are active, the short-circuit immediately permits the call to
continue instead of processing policy stages that have nothing to evaluate.
The governance gate could be placed below or above this early return. Placing it
below required a smaller change to the inherited control flow, but a default
installation with no active pre-tool-call plugin hook, trusted tool policy, or
tool-specific approval rule would reach the short-circuit first. The function
would then return before the governance policy was evaluated, allowing the tool
call to proceed without governance policy enforcement. The dashboard and policy files
could consequently exist even though their rules had no effect on agent
actions.

The gate was therefore placed above the short-circuit as the outer governance
boundary. It evaluates the attempted tool call before the optional policy
stages. A refusal prevents execution, an unresolved approval request pauses or
refuses the action, and a permitted call continues through the host's remaining built-in security
checks and any registered plugin hooks. The governance gate therefore adds an
enforcement boundary without bypassing or replacing the host's existing
controls. The separate runtime that did
not originally enter this function requires an additional interception method,
which is compared in the following subsection.

\subsection{Host Interception}
\label{sec:gov-host-interception}
% MATERIAL: "→ 3.4" §3.4.y, §3.5.15.

The central governance gate is reached directly when an agent runs inside the
OpenClaw Gateway, the long-running Node.js process started by
\texttt{openclaw gateway}. In this arrangement, the Gateway executes the
agent's tools and passes each tool call through
\texttt{runBeforeToolCallHook}, which contains the governance gate, a function called \texttt{evaluateGovernancePolicy}. OpenClaw also supports Codex, OpenAI's locally running coding agent, as a
secondary execution backend. In this arrangement, the agent and its tools run
in a separate Codex app-server process started through OpenClaw's native
harness.

OpenClaw already provides a native hook relay for communication between the
Codex app-server process and the Gateway. At session startup, OpenClaw can add a
\texttt{PreToolUse} hook command to the Codex session configuration. Before
Codex executes a matching tool call, this command sends the tool name and
arguments to the Gateway-side relay and waits for an allow or block response.
Since the governance project did not introduce the relay mechanism, its design had to
ensure that the existing relay was enabled for governance and applied to every
Codex tool call.

A pre-tool-call policy is a rule or callback evaluated before a requested tool
is executed. It can permit the call, block it, request human approval, or
replace its arguments. OpenClaw uses
\texttt{nativeHookRelayEventHasLocalWork} to determine whether a Codex
\texttt{PreToolUse} event must be relayed to the Gateway. The inherited
implementation enabled the relay when \texttt{hasBeforeToolCallPolicy} found a
registered plugin hook or trusted tool policy, or when the host's tool-loop
detector required the event. The built-in governance gate was not included in
those conditions. An installation with no applicable plugin policy and a
disabled loop detector could therefore start Codex without the
\texttt{PreToolUse} relay. Its tool calls would execute without reaching
\texttt{runBeforeToolCallHook}, so governance rules, audit logging, and session
control would not apply.
Three approaches were considered. The first was to widen
\texttt{hasBeforeToolCallPolicy} so that it also reported the governance gate.
This required a small change, but it would alter a shared Boolean check whose
specific purpose is to report whether plugin hooks or trusted tool policies
exist, causing other parts of OpenClaw to incorrectly treat the built-in
governance gate as evidence that plugin-based policy processing is active. It
could thus enable the relay in host configurations that deliberately
disable plugin-based pre-tool-call processing.

The second approach, which was the one selected, was to add the independent \texttt{governanceRequiresNativeToolRelay} signal.
The existing Boolean check continues to report plugin hooks and trusted tool
policies, and the additional signal reports whether the built-in governance
gate requires the Codex app-server process to consult the Gateway. The relay is
configured when governance, an existing pre-tool-call policy, or the loop
detector requires it. When governance activates the relay, the function
\texttt{nativeHookRelayEventToolMatcher} also configures it to cover every
Codex tool instead of inheriting the narrower tool list of an unrelated plugin
policy.

The third approach was to configure the relay only when governance was active
at the start of the Codex session. This could avoid unnecessary relay processing
when governance was off, but the relay configuration is created only once at session startup. If an operator enabled governance after the session had
started, the running Codex app-server process would not automatically gain the
missing relay. Its tool calls would continue bypassing the governance gate until
the session ended and a new one began. The selected design therefore uses
\texttt{governanceRequiresNativeToolRelay} to configure the relay at the start
of every governed installation's Codex session. A later change to the
governance posture can take effect immediately, because the communication
path to the governance gate already exists.

\subsection{Path Representation}
\label{sec:gov-path-representation}

To allow operators to define portable file-access rules, the system requires a
consistent path representation that does not depend unnecessarily on one
machine's directory layout. Paths are therefore normalized into canonical
strings, and path rules are expressed as regular expressions evaluated against
those strings. The chosen representation affects both portability and
security. Three
representations were considered. The first was to convert every path to an
absolute form. This is unambiguous after traversal components and symbolic
links are resolved, but it makes each rule dependent on one machine's directory
layout. A rule written on the Windows development machine would not apply to
the corresponding project directory on the Linux deployment server.

The second alternative was to use a workspace-relative form for every path.
This keeps project rules portable. However, it cannot safely represent a resource outside the workspace. Such a path would either have to be rejected even when access was
legitimate or represented with parent-directory components, reintroducing the
same traversal notation that canonicalization is intended to remove.

The selected representation is hybrid. A path inside the workspace is recorded
in workspace-relative form, and a path outside it is recorded as a canonical
absolute path. The path is resolved before this choice, including the removal of parent-directory components and the resolution of symbolic links. Leaving the workspace therefore changes the representation to an absolute path. A rule
anchored to a relative project directory cannot match an attempted escape.

Testing later exposed a second representation problem within the selected
approach. A file inside the workspace has both a legitimate relative name and a
legitimate absolute name, but an operator does not control the working
directory of the session that evaluates the rule. The final design thus
records the portable hybrid form but tests an in-workspace path against both
its canonical relative and canonical absolute forms. A path outside the
workspace receives only its absolute form, never a form containing
parent-directory components. This preserves the traversal defense and allows
rules written in either legitimate form to operate as intended.

\subsection{Log Integrity}
\label{sec:gov-log-integrity}

The first log-integrity decision was whether to extend OpenClaw's existing
\texttt{audit\_events} SQLite store or create a separate governance ledger. The
existing store already provides structured audit records, bounded retention,
and pseudonymized identities. It does not link one entry cryptographically to
the next as required by Requirement 6.

A separate append-only governance ledger was therefore selected instead of
extending the existing schema and writer. This allowed the record format,
cryptographic chain, and verification procedure to be designed around policy
decisions, agent actions, and administrative actions without coupling their
integrity guarantees to OpenClaw's general audit store. Keeping these events in
one sequence for each organization also preserves the relationship between an
administrative change and the agent action that followed it.

Three cryptographic structures were considered for the separate ledger. A bare
SHA-256 hash chain would detect accidental corruption and edits that were not
followed by recomputation, but an attacker who could rewrite the file could
recompute every later hash. A Merkle tree would support efficient proofs that
individual entries belong to a large or distributed log. The governance ledger is stored and verified on one machine, and verification
checks every entry from the beginning of the ledger to its end. Efficient proofs
for individual entries are therefore unnecessary, so a Merkle tree would add
the complexity of constructing the tree and managing its root hash without
providing a capability required by this system.

The selected structure is a sequential HMAC-SHA256 chain protected by a
per-installation key. Each entry's HMAC covers its own canonical fields and the preceding
entry's hash, so modification, insertion, deletion within the sequence, or
reordering causes verification to fail. However, the chain alone cannot detect
the removal of entries from its end. For example, if a ledger originally
contains 100 entries and the final ten are removed, the first 90 still form an
internally valid chain because entry 90 contains no record of entry 91, which once existed. A separate checkpoint therefore records the sequence number and hash
of the latest entry, collectively referred to as the chain head. Comparing the remaining chain head with the latest successfully written
checkpoint exposes truncation that removes entries covered by that checkpoint. This design provides stronger tamper evidence than
an unkeyed hash chain with less structural complexity than a Merkle tree.

In the evaluated deployment, the ledger, checkpoint, and ledger key are stored
on the same host. An attacker capable of destroying or replacing all three
could therefore conceal a rewritten or deleted history. Stronger protection
would require storing the key outside the host, regularly exporting the
checkpoint to a trusted off-host store, or applying both measures. This
deployment extension is outside the scope of the project and is retained as
future work.

\subsection{Operator Identity}
\label{sec:gov-operator-identity}
% MATERIAL: §3.5.6, §3.5.19.

Two operator-identity designs were considered. The first reused the existing
Gateway authentication credential as the sole identity for governance. This
approach required no additional account store or login session, and it retained
the host's established protection for access to the Control UI. Successful
Gateway authentication proves that a client may reach that interface. It does
not identify the particular person issuing a governance request. An
administrative action therefore cannot be attributed to a named operator, and
one of the four governance tiers cannot be assigned to that operator.

The second design added named governance accounts with independent login
sessions. This design was selected because the Root, Administrator, User, and
Viewer roles require identities whose permissions and agent scopes can differ.
Named accounts also provide the operator identity stored with each audit-ledger
entry. Management actions are therefore not recorded under one shared
identity.

The selected design does not replace Gateway authentication. Every governance
request must first pass the Gateway's existing access gate and then authenticate as the appropriate governance account. The first gate protects access to the host's management interface. The second
handles authentication into a human operator's designated governance role.

This approach adds an account store, password hashing, login throttling,
session expiry, and session revocation, all described in Section \ref{sec:two-gt-auth}. This cost was accepted because a single
shared credential could not satisfy both role-based access control and
individual accountability. Separating the two identities also preserves the
Gateway's original security boundary.

\subsection{Management Surfaces}
\label{sec:gov-management-surfaces}
% MATERIAL: §3.5.77.

The governance layer was initially to provide three management components: an HTTP
control plane, a dashboard built on that control plane, and a command-line
interface. Two alternatives were considered after the command-line surface had
been designed. The project could retain all three, or it could concentrate
operator management in the dashboard and its HTTP control plane.

Retaining the command line offered two benefits. It could provide a recovery
surface if the Gateway were unavailable, and it could serve as an independent
cross-check of dashboard behavior. These benefits came with a separate set of
commands, authentication behavior, documentation, and tests that duplicated
operations supported by the control plane. Parts of the command-line
implementation also depended on process-local state, so they could not observe
runs owned by the Gateway process. The project requirements did not call for a
command-line management interface.

However, the selected design retains two management components. The HTTP
control plane defines the governed operations and authorization checks, and the
dashboard provides the human-facing interface to them. The general-purpose
governance command line was removed before it was fully implemented because it was outside the scope of the project as set out by the requirements, and it was decided that time would be better spent developing and testing the surfaces that would be used most often by human operators. This removal does not weaken enforcement because agent
actions are checked at the central pre-execution gate, independently of the
surface used to configure policy.

One command-line utility was retained for a specific purpose. The CLI provides a tool to verify the audit ledger, independently of the same feature on the dashboard. This is to allow redundancy in ledger verification, that the ledger has not been tampered with. However the CLI has no tools to
create accounts, change policy, control agents, or open a management session.
It preserves the useful independent check without implementing a second set of tools for
administrative changes.

\subsection{Tenancy Model}
\label{sec:gov-tenancy-model}
% MATERIAL: §3.5.89.

A tenancy model defines how organizations share, or do not share, one deployed
system. Two models were considered. Under the first model, one OpenClaw
installation could host several organizations, each with its own Root account,
users, agents, policies, and audit records. Under the second model, each
installation would allow only one organization. Supporting another organization
would, thus require another installation. Although the first model would
reduce the number of deployed Gateway instances, it would require strict
separation of every resource and control shared by those organizations.

This becomes difficult when it is considered that some controls are installation-wide, such that a particular setting may affect the
entire OpenClaw installation. For example, the secondary runtime backend, which
runs agents through a separate Codex app-server process as described in
Section~\ref{sec:gov-host-interception}, is controlled for the whole host. If
several organizations shared the installation, an operator from one
organization could affect a service used by the others without having authority
over their accounts or agents. Preventing this interference would require a
different deployment boundary or an arbitration model. A deployment boundary
defines which components are administered together, and an arbitration model
defines how conflicting decisions made by different organizations are
resolved.

The selected design therefore permits one organization per installation. The
first Root account establishes the organization, and the system refuses attempts
to create another organization within the same installation. A second
organization requires a separate installation. This design places all
installation-wide controls under one accountable Root and does not claim to
provide simultaneous isolation between multiple organizations.

The internal records remain organization-scoped, meaning that each record is
associated with a specific organization identifier. Accounts, agents, policies,
audit ledgers, rule requests, and attachments either store or derive this
identifier. This structure remains useful under the single-organization model
because the restriction applies to simultaneous organizations, not necessarily
to the entire lifetime of an installation. If an organization on an installation is deleted, its
retained audit records remain distinct from the records of any successor.
Organization identifiers also allow the system to perform explicit ownership
and registration checks. Removing them would require replacing those checks
without providing a visible benefit to the operator.

\section{Developed Design}
\label{sec:gov-developed}

The developed system places governance inside the OpenClaw Gateway and applies
it through two related paths:
\begin{enumerate}
\item The operator path handles authenticated management requests from the Governance dashboard. 
\item The agent path intercepts tool calls
before their requested actions are performed. 
\end{enumerate}
Both paths use the same account,
agent, policy, and audit state, which keeps them aligned in functionality, preventing the dashboard from
presenting controls that are not enforced during agent execution.

The design is divided into components with distinct responsibilities:
\begin{itemize}
    \item The policy engine decides whether an attempted action may proceed.
    \item The audit ledger records agent and administrative activity.
    \item The access-control model determines which human operator may perform each management operation.
\end{itemize}
Session controls,
human-in-the-loop approvals, and runtime management allow operators to intervene
during execution. The tenancy model, agent registry, management interface, and
security controls establish the ownership and deployment boundaries around
these components. 

The following sections describe each component as implemented,
including its purpose, operation, and relevant internal design decisions.

The governance layer operates inside the OpenClaw Gateway, the long-running
Node.js process started by \texttt{openclaw gateway}. It has two entry paths:
an operator control path for management requests and an agent enforcement path
for tool calls. Figure~\ref{fig:gov-architecture} presents these paths, the
components they pass through, and the state they share.

An operator reaches the Governance page through the Control UI, which is
accessed through an SSH tunnel and not directly through the public
internet. Every governance HTTP request passes through two independent
authentication gates. The first is OpenClaw's existing Gateway authentication,
which establishes that the client may access the Gateway. The second is the
governance account session, which identifies the individual operator and
provides the role, organization, and agent scope used for authorization.
Passing the Gateway check therefore does not grant governance authority by
itself. The request must also be permitted for the signed-in governance
account before a route under \texttt{/control-ui/governance} performs an
operation.

Agent activity enters through the pre-execution tool-call path. Before an
in-process tool call executes, the Gateway passes it through
\texttt{runBeforeToolCallHook}. This function invokes
\texttt{evaluateGovernancePolicy}, the central governance decision function.
The decision function resolves the registered agent and its organization,
identifies and normalizes the requested resource, reads the applicable policy,
and produces an \texttt{allow}, \texttt{deny}, or \texttt{ask} decision. An
allowed call continues to the requested tool. A denied call returns a refusal
without executing the tool. An \texttt{ask} decision holds the call until an
authorized operator answers or the request expires. Calls that have no
governable resource are recorded separately as \texttt{ungoverned} instead of
being presented as policy-approved actions. Figure~\ref{fig:gov-code-central-interception} shows the code of this interception in the
tool adapter, the Gateway wrapper that prepares each tool
call and passes it through the shared pre-execution checks. The adapter awaits \texttt{runBeforeToolCallHook} and converts a
veto into a refusal before the requested tool implementation is
invoked.

Both paths use governance state stored under
\texttt{\textasciitilde/.openclaw/governance/}. Installation-wide records
include the account store, session store, agent registry, ledger key, and ledger
checkpoint. Organization-scoped records are stored below
\texttt{groups/<groupId>/} and include the policy document, audit ledger, rule
requests, attachments, conversations, and pending decisions. The system allows only one organization per installation, but retaining explicit
organization identifiers prevents retained records from being confused with
those of a later organization.

The architecture does not introduce a separate policy server or database
service. Policy evaluation, authorization, administrative operations, and audit
writing execute through the Gateway and its governance modules. This keeps the
enforcement point on the same execution path as the actions it controls. It
also ensures that the dashboard and the tool-call gate read the same policy and
ownership state rather than maintaining separate interpretations of the
governance configuration.

\subsection{Policy Engine}
\label{sec:gov-gate}
% MATERIAL: §3.5.4, §3.5.12, §3.5.20; PERMISSION-SPEC.md.
The policy engine is the component that derives an enforcement
decision from an attempted agent action and the relevant policy. Its central
function, \texttt{evaluateGovernancePolicy}, is called before the requested
tool executes. The function does not ask the language model whether its own
action is safe. Instead, it evaluates stored rules and system invariants
outside the model's reasoning process, preventing generated text from
overriding the decision.

To make a policy decision, the engine first
establishes the canonical identity of the agent and the organization that owns
its policy. It then uses the tool definition to identify the governed resource,
such as a command, network destination, or file path. File paths are
canonicalized before matching, and other resource values are normalized into
the form required by the rule language. The engine also enforces controls that
are not ordinary operator-authored rules, including agent registration,
lockdown, and permission to use the secondary runtime backend.

The applicable policy contains immutable core denials, baseline rules supplied
with the installation, and rules created by authorized operators. The engine
evaluates these layers with denial precedence: a matching denial cannot be
overridden by a matching allowance only because the allowance appears later.
If no rule supplies a final allowance or denial, the configured
human-approval behavior determines whether the call is refused immediately or
held for an operator. The following subsections describe the rule vocabulary,
evaluation sequence, path handling, baseline policy, and directory-grant
mechanism.

Every completed evaluation produces an auditable outcome. An allowed call
continues, and a path-based call may receive canonicalized parameters so that
the tool acts on the same path that the engine evaluated. A denied call is
stopped before execution and returns a reason for the refusal without
revealing protected information. An \texttt{ask} decision remains associated
with the pending action until an authorized answer or a timeout resolves it.
The policy engine therefore supplies both the decision and the enforcement
result used by the surrounding Gateway.

\subsubsection{Rule Model}
% T70 (2026-09-27): the code figure now shows `description: string` (required). A paragraph on the field (required, at most 500 characters, trimmed, shown as each rule's title, recorded in the ledger) is drafted in docs-notes/report/T70-FOR-THE-REPORT.md for Kinan to adapt.

A human operator writes a rule through the governance dashboard, which is then stored as TypeScript types in the backend in a particular form, or rule model. This rule model is defined by the TypeScript types in
\texttt{src/governance/policy-types.ts}. Its central structure is
\texttt{PolicyRule}, shown in
Figure~\ref{fig:gov-code-rule-model}. Each rule identifies the resource being
governed, states whether access is allowed or denied, and defines the scope and
lifetime of that decision. Keeping this structure in one type definition gives
the policy engine, policy store, and management interface the same
interpretation of a rule.

The \texttt{resourceKind} field separates the language into
\texttt{command}, \texttt{path}, and \texttt{network} rules. A command rule is
matched against an extracted command, a path rule against a canonicalized file
location, and a network rule against a normalized destination. The union type
in Figure~\ref{fig:gov-code-rule-model} prevents a rule from naming an
unsupported resource family. The policy engine also compares a rule only with
a resource of the same kind, so a command allowance cannot authorize a file or
network operation.

The \texttt{pattern} field contains a regular expression tested against the
extracted resource. This representation supports narrow rules for one exact
resource and broader rules covering a directory or destination family.
Patterns are validated before storage to ensure that they compile, remain
within the configured length limit, and do not contain known unsafe
regular-expression structures. The engine therefore evaluates a bounded,
previously validated pattern rather than accepting unchecked expressions during
each tool call.

The \texttt{effect} field assigns either an \texttt{allow} or
\texttt{deny} effect. An omitted effect means \texttt{allow}, as indicated in
Figure~\ref{fig:gov-code-rule-model}. A denial is stricter
than the absence of an allowance because it can refuse a specific resource
even when a broader allowance also matches. The engine therefore evaluates
denials before allowances.

The optional \texttt{access} field narrows a path rule to \texttt{read} or
\texttt{write}. When it is absent, the rule applies to both directions. This
distinction allows a policy to grant inspection of project files without also
granting permission to modify them. Access direction applies only to path
rules because commands and network destinations do not have an equivalent
read-and-write distinction in this policy model.

The \texttt{tier} field assigns a rule to \texttt{core},
\texttt{baseline}, or \texttt{admin}. An omitted tier means
\texttt{admin}.
Core and baseline rules are both supplied with the installation, but they serve different purposes. Core rules are security restrictions that establish the minimum protection the system must retain. The policy store reconstructs them from source whenever the policy is loaded, preventing a stored document from deleting a core restriction or introducing a false core-tier allowance. Baseline rules are explicit starting permissions that allow a newly installed agent to perform limited, ordinary work under the default-deny posture. Operators may alter these starting permissions as operational requirements become known. Admin-tier rules record those later operator decisions. In summary, core rules define the security floor, baseline rules provide a usable initial allowlist, and admin rules adapt that allowlist to the deployment.

Some core rules carry the \texttt{selfProtecting} marker shown in
Figure~\ref{fig:gov-code-rule-model}. These rules protect the governance
directory, account records, audit ledger, and the controls that could disable
the governance layer. They cannot be disabled at runtime, including by the
Root account, because removing them would allow a governed agent to interfere
with the mechanism that governs it. Other core denials, including credential
protections, may be disabled by Root through a deliberate and recorded policy
decision.

The optional \texttt{agentId} field determines a rule's scope. Its absence
makes the rule global, so it applies to every registered agent in the
organization. When the field is present, the policy engine considers the rule
only for the named agent.
Global restrictions and applicable agent-scoped restrictions are both
consulted during an evaluation.

The \texttt{createdAt} and optional \texttt{expiresAt} fields describe the
rule's lifetime. An absent expiry denotes an indefinite rule. Before matching,
\texttt{isRuleExpired} parses the expiry and excludes a rule whose time has
passed. An invalid timestamp is also treated as expired, so malformed data
cannot transform a temporary permission into a permanent one. The
optional \texttt{createdBy} field records the governance account responsible
for an operator-authored rule.

Figure~\ref{fig:gov-code-rule-examples} shows how these fields combine in two
representative rules. The first is a temporary, agent-scoped allowance. It
permits one agent to read the \texttt{src} directory but does not permit
writing to it. The second is a global, self-protecting core denial that prevents
agents from reaching governance state.

The engine first obtains the effective agent identifier and calls
\texttt{resolveAgentGroup}. An unregistered agent has no organization policy,
so the call is refused before rule evaluation. Because no organization ledger
exists for that agent, the engine writes an
\texttt{agent-not-registered} entry to the ledger. The
returned reason directs the operator to register the agent.

For a registered agent, the policy engine loads the organization policy and checks
its posture. The \texttt{off} posture returns at this point, before lockdown
or resource evaluation, and creates no policy-decision record. It therefore
means that the governance gate is inactive, not that the policy explicitly
allowed the call. Registration is still checked first because the engine must
identify the organization policy before it can read its posture.

An active policy next applies containment and execution-environment controls.
The engine refuses an agent under direct or inherited lockdown. It also
refuses a native per-agent backend request when the agent lacks permission for
that backend. These checks remain effective in \texttt{monitor} posture. In this posture, the engine records what enforcement would have decided but allows ordinary policy misses to proceed. The checks are administrative prerequisites, so a resource allowance cannot override
them.

The policy engine then looks up the governed-tool specification for the requested
tool. The specification defines its resource kind, access direction, and
resource extractor. Path tools also resolve their parameters before matching,
and the resolved binding can be passed onward to the tool. This ensures that
the tool operates on the same path that the policy was evaluated. The complete
path-normalization process is described in the following subsection, Section \ref{sec: path-canonz}.

Default-deny applies after a governed tool has been recognized and at least
one resource has been extracted. If the tool has no governed-tool
specification, the engine records an \texttt{ungoverned} result with the
reason \texttt{no-extractor}. If a specification exists but extraction
produces no resource, it records
\texttt{no-resource-extracted}. The engine does not classify either result as
\texttt{default-deny}, and the host pipeline may continue the call. These
records expose gaps in governance coverage so that an operator can distinguish
an unsupported tool integration from an action approved by policy.

Successfully extracted resources enter two rule passes. The first pass selects
all rules whose effect is \texttt{deny}. A candidate denial must have the same
resource kind as the tool, cover its access direction, remain unexpired, and
be either global or scoped to the evaluated agent. The engine then tests its
pattern against the normalized forms of each resource. This pass includes
\texttt{core}, \texttt{baseline}, and \texttt{admin} denials. Tiers determine
rule ownership and mutability; every active denial has the same runtime force.

If a denial matches, the engine records every resource rejected by a denial
and blocks the complete call. The returned explanation names the first
refusal, keeping the model-facing message concise, and the ledger retains the
other matching refusals. No allowance can reopen the call because the denial
branch returns before the allowance pass begins.

Figure~\ref{fig:gov-code-evaluation-order}, the allowance filter uses
\texttt{effect !== "deny"}. It therefore accepts an explicit
\texttt{allow} effect and the \texttt{undefined} value, which results from omitted policy field values. The omission does not change the result for a resource that
matches no rule.

The allowance pass applies the same resource-kind, access, expiry, and
agent-scope restrictions. Each extracted resource must match an active
allowance for the complete call to proceed in \texttt{enforce}. For example,
if a file-editing operation names three paths and only two match allowances,
the third path causes the whole invocation to miss policy. The operation is
not divided into permitted and unpermitted parts.

Every resource evaluated in the allowance pass receives a ledger entry. A
matched resource records \texttt{allow} and the identifier of its rule. An
unmatched resource records the reserved rule identifier
\texttt{default-deny}. Its decision is \texttt{deny} when asking is disabled
and \texttt{ask} when approval is enabled. The ledger entry also contains the
agent, session, tool, resource kind, normalized resource, and model intent.
This resource-level recording exposes the full scope of a multi-resource
request.

The policy engine resolves approval behavior through
\texttt{resolveAskingAccounts} and \texttt{resolveAskMode}. In
\texttt{enforce}, an uncovered resource is refused immediately when asking is
off. When asking is enabled, the engine returns an approval request using the
timeout selected by \texttt{resolveHitlTimeoutMs}. An
\texttt{allow once} answer authorizes the pending call, and a
\texttt{deny} answer refuses it. An \texttt{allow always} answer authorizes
the pending call and files a rule request for later Administrator or Root
review. It does not insert a rule directly into the active policy. An
unanswered request fails closed when its timeout expires.

The \texttt{monitor} posture preserves the evaluation and ledger steps but
changes the treatment of an ordinary policy miss. The engine records the
decision that \texttt{enforce} would produce and then permits the call.
Matching denials still block because they return before posture handling.
Registration, lockdown, and backend authorization also remain mandatory.
Under \texttt{off}, in contrast, the engine returns after loading the policy, so tool calls are neither evaluated nor recorded as policy decisions. Other aspects are still recorded in the audit ledger however.

Creation order does not affect runtime precedence. Rule creation may identify
an earlier conflicting rule to explain an authoring conflict, but this message
does not create a first-rule-wins evaluator. During enforcement, any matching
denial takes precedence over every allowance, regardless of when the rules
were created. If no denial matches, the call proceeds only when all governed
resources match active allowances or the configured posture permits an
ordinary miss.

The resulting order separates organizational identity, administrative
containment, resource identification, policy matching, and enforcement.
Registration selects the policy owner; lockdown and backend checks determine
whether the agent may act; extraction identifies the affected resources; the
two rule passes determine the policy result; and the posture determines how an
unmatched resource is handled. This separation prevents a resource allowance
from overriding a stronger administrative or denial decision.

\FloatBarrier
\subsubsection{Path Canonicalization}
\label{sec: path-canonz}

A path rule is evaluated against a string, but several different strings can
refer to the same file. For example, a relative path, an absolute path, and a
path containing a symbolic link may all reach one location. A symbolic link is
a filesystem entry that redirects one path to another. If the policy engine
matched only the text supplied by the agent, the rule could approve a name that
leads to a different location. The engine therefore canonicalizes each path
before rule evaluation, reducing its different spellings to a stable
representation of the location it reaches.

Path handling is implemented by \texttt{resolveGovernedPath} in
\texttt{src/governance/path-normalize.ts}. The function returns three related
values: the resource string used by policy rules, the canonical absolute path,
and a Boolean value named \texttt{redirected} that states whether resolution
changed the file addressed by the original path. The shorter
\texttt{normalizeGovernedPath} function returns only the resource string for
callers that do not need the other values.

The path extractors in
\texttt{src/governance/resource-extraction.ts} apply this process to file
tools. The \texttt{read}, \texttt{write}, and \texttt{edit} tools obtain their
path from the \texttt{path} or \texttt{file\_path} parameter.
\texttt{apply\_patch} provides host-derived paths through
\texttt{derivedPaths}. The search tools \texttt{grep}, \texttt{find}, and
\texttt{ls} are also treated as path reads. When one of these search tools
omits its optional path, the extractor uses \texttt{.}, meaning the session's
current workspace, because that is where the tool searches by default.

that attempts to leave the workspace.

The first stage calls \texttt{resolveToCwd} using the working directory supplied
in the tool-call context. This directory is the session workspace against which
relative paths are interpreted. The helper expands the home-directory shortcut
\texttt{\textasciitilde}, interprets a valid \texttt{file://} value as a local
path, and joins a relative path to the workspace. Node.js path resolution then
collapses \texttt{.} and \texttt{..} components. The result is an absolute path
that describes where the agent's input leads before symbolic links are
considered.

Collapsing parent-directory components prevents an apparently permitted prefix
from controlling the result. With \texttt{/workspace} as the working
directory, the input \texttt{src/../../etc/passwd} begins with
\texttt{src/}, but resolving it produces \texttt{/etc/passwd}. The pattern
\texttt{\^{}src/.*\$} is therefore tested against the external location rather
than the misleading input text. The system does not search for particular
dangerous spellings. It resolves the path and applies the ordinary rule to the
result.

The second stage calls the asynchronous filesystem function
\texttt{realpath}. A real path is the location obtained after the filesystem
has followed every symbolic link in the supplied path. The asynchronous form is
used because canonicalization occurs in the Gateway's pre-execution path. The
Gateway can continue handling other work while the operating system resolves
the requested location.

A static symbolic-link escape is handled by this stage. Suppose
\texttt{/workspace/notes} is a link to \texttt{/etc}. Resolving
\texttt{notes/passwd} produces \texttt{/etc/passwd}. The resulting resource is
outside the workspace, so an allowance covering
\texttt{\^{}notes/.*\$} does not apply. The rule is evaluated against the
destination of the link rather than the link name.

A requested path does not always exist. Creating a new file is a normal write
operation, so failure to resolve the complete path cannot automatically end
canonicalization. The internal \texttt{canonicalize} function walks upward
until it finds the deepest existing ancestor, resolves that ancestor, and then
reattaches the missing path segments. For example, if
\texttt{/workspace/data} is a symbolic link and the requested path is
\texttt{data/new/reports/output.txt}, neither \texttt{new} nor its descendants
may exist. The function resolves \texttt{data} first and appends the remaining
segments to its destination. A link in an existing parent directory therefore
continues to affect the path that the policy evaluates.

The workspace root is canonicalized as well. This matters when the workspace
directory is itself reached through a symbolic link, as may occur on a managed
Linux host. Comparing a canonical file path with an unresolved workspace path
could incorrectly classify an ordinary project file as external. Resolving both
sides gives the containment check one consistent filesystem view.

After resolution, \texttt{formatPathRelativeToCwdOrAbsolute} selects the
resource stored in the ledger. A location inside the workspace is represented
relative to that workspace and uses forward slashes, such as
\texttt{src/app.ts}. This form keeps project rules independent of the
installation directory. A location outside the workspace is represented by
its canonical absolute path, such as \texttt{/etc/passwd}. The change to an
absolute representation makes a workspace escape visible to the rule engine.

Path processing respects the host operating system's filename rules. On
Windows, a backslash is a directory separator and path comparison ignores case
when deciding whether two spellings address the same file. On Linux, a
backslash is a valid character within a filename, and case remains significant.
Treating the platforms identically would cause the policy engine to evaluate a
different filename from the one used by the operating system.

The recorded resource is not the only form used for matching. The function
\texttt{resolveGovernedPathForms} returns every valid rule-facing form of the
resolved location. An in-workspace path has two forms: its workspace-relative
name and its canonical absolute name. Rules are tested against both because an
operator may write either representation. The ledger and refusal messages
retain the workspace-relative form so that records remain readable and
portable.

An external path receives only its absolute form. The engine never constructs
a relative form containing \texttt{..} for a location outside the workspace.
Consequently, testing both forms for an internal path does not weaken traversal
protection. A path receives a relative form only after the containment check
has established that it is inside the canonical workspace.

Canonical matching alone is insufficient if the tool later resolves the
agent's original path again. The period between checking a path and using it is
called a time-of-check-to-time-of-use, or TOCTOU, window. During that interval,
a symbolic link could be redirected from the approved file to another target.
Both resolutions would be valid when they occurred, but the tool would open a
file that the policy engine had not evaluated.

The policy engine closes this link-redirection window through
\texttt{resolveGovernedParamBinding} in
\texttt{src/governance/policy-engine.ts}. Here, binding means replacing the
tool's path parameter with the canonical absolute path that was evaluated. The
function operates on path tools carrying \texttt{path} or
\texttt{file\_path}. It creates a replacement only when
\texttt{resolveGovernedPath} reports that symbolic-link resolution redirected
the call. An ordinary path that already addresses its canonical location keeps
its original parameters.

Binding occurs before resource extraction. The policy engine first produces
the replacement parameters and then gives those parameters to the extractor.
The extracted resource, the rule-matching forms, and the path returned to the
tool therefore originate from the same resolution. This ordering prevents two
independent resolutions inside the policy engine from disagreeing if a link is
changed between them.

When the call is permitted,
\texttt{runBeforeToolCallHook} applies the returned parameters before later
approval checks, trusted policies, plugin hooks, and the tool implementation
run. These stages consequently receive the same file selected by governance.
The binding also applies in \texttt{monitor} posture. Monitor may allow a
policy miss to proceed, but the file opened by the tool must still be the file
named in the ledger.

The replacement is deliberately limited to calls that contain a path parameter.
An \texttt{apply\_patch} call supplies host-derived paths rather than
\texttt{path} or \texttt{file\_path}, so the policy engine has no tool
parameter to replace. A refused call is not rebound because it will not
execute. These limits keep unrelated tool parameters unchanged.

Canonicalization and binding close parent-directory traversal, static
symbolic-link escapes, and link redirection after an allowed decision. They do
not prevent every filesystem race. A process with sufficient access could
replace the file at the canonical path after evaluation. For a file that does
not yet exist, a link could also be created at the final path segment before
the tool opens it. Preventing these cases would require the tool to operate on
an already opened filesystem handle rather than resolving a path during
execution.

Recursive search tools introduce a separate boundary. Governance evaluates and
binds the directory from which \texttt{grep}, \texttt{find}, or \texttt{ls}
starts, but the pre-execution parameters do not identify every descendant the
tool may later inspect. Controlling each visited file would require the tool to
report those files during or after execution. These remaining filesystem
