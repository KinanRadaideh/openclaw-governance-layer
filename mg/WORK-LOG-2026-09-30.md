### The legitimate door

`POST policy/agent-mode` (`src/gateway/governance-dashboard-api.ts:591`): Gateway auth, then a
governance login cookie with role **Administrator or higher**, then the agent must be in the
actor's scope. `off` is refused for one agent at every tier (`PER_AGENT_OFF_REFUSED`). Every
change writes `governance.policy.agent-mode` to the ledger. A User can only _request_ it
(agent-setting request, Administrator decides). Floor pinned by
`governance-privilege-matrix.test.ts`.

### Agent-side doors, measured

| `write` / `edit` / `read` on `policy.json` (absolute)                | block     |
| `write` via `../` traversal from the workspace                       | block     |

(`apply_patch` without `derivedPaths` answered allow: a probe artifact, since the production hook
always derives them. It is the "drive the production caller" lesson again.)

### What an out-of-band write gets

`loadPolicy` keeps a hand-written per-agent `monitor` (it drops only a per-agent `off`, finding 80) and keeps an installation-wide `mode: "off"`. Measured: `curl … | sh` block → allow after
`agentMode: {agent-a: monitor}` was written to the file; the core denials, the governance-dir
denial and the kill switch still blocked under monitor; a global `off` allowed everything; a
per-agent `off` was dropped (still blocked). No ledger entry is written for a file edit; the
deployment report's "Governance is enforcing" check warns on a monitored agent.

### Conclusion

Protected on every surface the agent has, **unless an operator grants a general-purpose
interpreter or shell with free arguments**. Then the command denials are a backstop that run-time
path construction defeats, and the agent can write `policy.json` (monitor, or global off), since
it runs as the same OS user as the Gateway. This is the residual `baseline-policy.ts`'s header
states (the allowlist is the boundary, the denylist a backstop) and Q-73b's note ("anyone who can
run these commands can also write `policy.json` directly"). Gap found: `describeRuleRisks`
(`rule-validation.ts`) gives **no warning** for `^python3? .*$`, `^node .*$`, `^bash .*$` etc.,
because they are anchored and not wildcard-only. Not fixed; offered to Kinan.

## Built: the `runs-arbitrary-code` warning (Kinan: "yes add the warning with tests")

`describeRuleRisks` (`src/governance/rule-validation.ts`) now warns on an **allow** command rule
that lets the agent hand code to an interpreter. It is probed, not parsed: the rule is run
through the gate's own `matchesPattern` against one concrete spelling for each of 22 programs
(python, python3, py, node, bash, sh, zsh, powershell, pwsh, cmd, perl, ruby, php, deno, bun, npx,
npm exec, pnpm dlx, env, awk, find -exec, git -c alias). Non-blocking, like every other warning.
It shows where the other warnings show: the add-rule response, and the approval preview of a
pending rule request. There is no UI change, because the UI renders warnings generically.
Denials, path/network rules, and rules already warned as granting everything are not warned.

Tests: 8 new in `rule-warnings.test.ts`. One checks the message's claim against the shipped core
denials: an assembled governance path passes `^python3? .*$` and no command denial. The one
failure on first run was the test's expected order ("python3 or node"), not the code.

tsgo core and core-test clean; full governance suite: see below.
