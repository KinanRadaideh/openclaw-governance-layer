## T73: what was measured before designing idea 2

Probed on this machine (scratchpad `aol/`), because idea 2's value depends on what the operating
system really enforces against a process running as the same user as the Gateway:

- An ACL granting the file's **OWNER RIGHTS** only `RD,REA,RA,AD,WA,WEA,D,RC,S` (read, append,
  write attributes, delete, read control, synchronize) plus SYSTEM full, applied with `icacls`.
- **Under a normal (non-elevated) token** (`runas /trustlevel:0x20000`): Node's `appendFile`
  works; `writeFile`, `truncate` and `open(r+)` fail with `EPERM`; the same user can no longer
  change the ACL (`icacls … /grant` fails, because OWNER RIGHTS removes the owner's implicit
  `WRITE_DAC`); `rename` works (so rotation keeps working, and the archive keeps the ACL);
  `unlink` works.
- Without `WA,WEA` Node's append fails too: libuv opens an append handle with
  `FILE_GENERIC_WRITE` minus `FILE_WRITE_DATA`, which still asks for write-attribute rights.
- **Under an elevated token** (this desktop session runs at High integrity) every write
  succeeds: libuv opens with `FILE_FLAG_BACKUP_SEMANTICS`, and an elevated administrator holds
  the backup and restore privileges, which override the ACL. PowerShell/.NET writes are still
  refused there, because they do not ask for backup semantics.
- So on Windows idea 2 refuses **in-place** truncation and overwrite by a non-elevated process,
  and does **not** stop deleting the file and writing a shortened copy. That case is what idea
  12 (the gap line) and idea 4 (the browser witness) catch. Linux needs root for `chattr +a`,
  and `+a` also forbids the rename rotation uses.

## T73: what was built

**Idea 12, the gap line** (`src/governance/audit-ledger.ts`). Inside the append lock, before
anything is written, `recordCheckpointDisagreement` compares the chain head with the checkpoint:

- checkpoint **ahead** of the head (entries cut from the end, or the active file replaced),
- the checkpoint's entry **replaced** (same number, different fingerprint),
- checkpoint behind the head and its entry **vanished** from the ledger,
- checkpoint **missing** although the head was written by a keyed installation.

Any of these writes a sealed **gap line** first: an `admin` entry by the labelled actor
`ledger-integrity`, action `governance.ledger.gap`, decision `ungoverned`, agent `-`, subject
`checkpoint:<seq>:<hash>` (or `checkpoint:missing`), with a sentence saying what was expected
and what was found. When the checkpoint is ahead, numbering continues from the checkpoint
(`checkpoint.seq + 1`), so no number is ever reused. Then the requested entry, then the
checkpoint. The normal crash state (checkpoint one behind, its hash equal to the head's
`prevHash`) and a checkpoint further behind whose entry is still there unchanged stay silent,
as before. One gap line per disagreement: if the checkpoint cannot be written, the finding is
remembered in-process so the next append does not record it again; a successful checkpoint write
clears that memory, so a second, later deletion is recorded again.

`verifyLedgerChain` accepts a numbering jump **only** on a gap line (recognised by actor, action
and `keyed`, then sealed-checked like every entry), keeps `ok: true`, and returns `alerts` (every
gap line and witness alert, with `missingFrom`/`missingTo` for a jump). The standalone
`scripts/verify-ledger.mjs` mirrors this and prints `INTEGRITY ALERT at entry #N (entries #a–#b
are missing)`.

**Finding 403, found on the way and fixed:** `scripts/verify-ledger.mjs` read only the active
file `audit-ledger.jsonl`, never the rotated archives `audit-ledger.jsonl.1…`, so after the first
rotation (8 MiB) an intact ledger was reported `BROKEN … unexpected sequence number (expected
1)`. It now reads the archives first, as the product's verifier always has.

**Also fixed on the way:** a rotation that failed (`rename` refused) threw **after** the entry and
its checkpoint were written, so the caller was told its action went unrecorded when it had been
recorded, and the gate refused the tool call. Rotation failure is now non-fatal, remembered, and
reported by the deployment report (`deployment.ledger_rotation`).

**Idea 2, append-only** (`src/governance/ledger-append-only.ts`). On Windows, every new ledger
file (first entry, and each new active file after rotation) gets the OWNER RIGHTS ACL measured
above, via `icacls`; archives keep it through the rename. Never throws: a failure is remembered
and reported. Off in test runs unless a test switches it on (dozens of suites tamper with ledger
files on purpose). `probeLedgerAppendOnly` measures the property (opens the file for read+write
without append and closes it) instead of reading configuration. On Linux nothing is applied; the
deployment report says an unprivileged process cannot do it and names `chattr +a` (root) and its
cost to rotation.

**Idea 4, the witness** (`src/governance/ledger-witness.ts`, route `integrity/witness`, Viewer and
above). The server issues `{groupId, seq, hash, receipt}` where `receipt` is an HMAC under the
ledger key with its own label (`openclaw-ledger-witness/v1`), so it can never be confused with an
entry seal. The browser keeps it in `localStorage` (every access guarded) and hands it back once
per sign-in. A valid receipt for an entry the ledger no longer holds as it was writes a sealed
`governance.ledger.witness-contradiction` alert naming the account whose dashboard held it; one
alert per fact (deduplicated against existing alerts, including a gap line about the same entry,
and against concurrent reports). A forged receipt, another organisation's, or another key's is
`unverifiable` and dropped.

**Idea 14, the alert** (`src/governance/ledger-alerts.ts`, routes `integrity/alerts`
Administrator, `integrity/acknowledge` Root). The list is derived from the chain, not stored
beside it: alerts and Root's acknowledgements are entries, and both must carry a valid seal, so
a line appended without the key can neither raise nor clear one. Read incrementally (only what
was appended since the last read; rebuilt after rotation, truncation, or when the last line read
is no longer where it was). The dashboard shows a banner above the sections to Administrators and
Root; Root acknowledges each alert with a required reason (≤ 500 characters), recorded as
`governance.ledger.alert-acknowledge`. The deployment report fails `deployment.ledger_alerts`
while any is unacknowledged, and reports it as `unknown` when the key is unusable (found by the
existing test suite: the new row first crashed the whole report).

**A defect in my own first version, caught by a test before it shipped:** the alert index
trusted its byte offset whenever the file was not smaller than before; a ledger cut and then
appended past the old length was read from the middle of a different line, and the gap line was
missed. It now re-reads the last line it read and rebuilds if it is not there unchanged.

**The page.** `governance-page.ts` was at exactly 700 code lines. The chain-verification state and
handler moved into the new `integrity-controller.ts` (same subject), which made room for the
controller, the banner and the refresh hook (697 after).

## T76: what was built

`src/governance/user-store.ts` `deleteAccount` (with `deleteUser` kept as its boolean wrapper):
inside the users-file lock, after every refusal (last Root, accounts left unmanaged, owned
agents), it **revokes the account's sessions, then removes the record**. Revocation failing
throws `SessionRevocationError` and nothing is deleted (route answers 503
`sessions_unavailable`, "was not deleted … then delete it again"); the record write failing
after revocation leaves the account signed out but present, the restrictive direction. After
that point of no return, `finishDeletedAccount` (`src/governance/account-deletion.ts`) sweeps the
sessions a second time, purges what was held under the name, and writes the ledger entry; each
failure is **reported** (`cleanupError`, `auditError`), never thrown. `users/delete/finish` (Root)
runs the same sequence again for an account that is gone, records it as
`governance.account.delete-finish` (so `userDelete` still counts each deletion once), and
refuses with 409 while any account holds the id or the name (the purge keys on the name).
The sign-in route now checks the account still exists after issuing a session and revokes it
if not, which with the second sweep closes the window between `authenticate` reading the account
and the session being written. The stale comment ("so the command line asks for the same word")
on `organisation/delete` is reworded. The dashboard shows Root "X was deleted, but not
everything was finished" with what is left and **Finish deleting**
(`ui/src/pages/governance/panels/account-deletion.ts`).

`normalizeAgentIds` moved to `src/governance/agent-ids.ts` (re-exported from `user-store.ts`) so
`user-store.ts` can import `session-tokens.ts` without the two importing each other.
