  request** (`proposeRuleFromEscalation`, `src/governance/policy-engine.ts`); the rule exists only
  once an Administrator approves the request (`rule-requests/decide`,
  `src/gateway/governance-dashboard-rule-requests.ts`), which called `addRule` with no `expiresAt`.
- So **every** rule made from a request, whatever filed it (the request form, "Always allow" on the

  route. A lifetime chosen there covers all of them.
- "Add a rule" takes `ttlMinutes` (`resolveRuleTtl`, `src/governance/rule-validation.ts`), capped at

  (`ui/src/components/exec-approval-card.ts`), drawn inline by `panels/approval-panel.ts`. Who

## 2. Decisions (by precedent; Kinan said decide and record)

- **E1. Scope is option A as written.** A lifetime on the approval of a rule request and beside
  "Always allow". The row's other two gaps, folder grants and agent assignments with no lifetime,
  are not in option A and are left; they stay in T86 as stated limits.
- **E2. "Always allow" proposes a lifetime; it does not set one.** It files a request, so the
  lifetime chosen beside it is stored on the request as `ttlMinutes` and counts from the
  **approval**, not from the answer. Counting from the answer would let a one-hour choice run out
  while the request waits in the queue, and the approved rule would be born expired.
- **E3. The approval decides.** `rule-requests/decide` takes `ttlMinutes`: a number of minutes
  grants that; `null` grants a rule that never expires; leaving it out grants what the request asked
  for. Precedent: the rule is built from the stored request so an Administrator grants what was
  reviewed (the comment in the route; finding 279 for `access`). An Administrator may make a
  proposed lifetime permanent because they may add a permanent rule outright. The dashboard always
  sends the field, so the grant is exactly what the row showed.
- **E4. The request form offers it too.** A11's precedent: the request form carries what "Add a
  rule" carries when approval grants it verbatim (it added the path direction for that reason).
- **E5. A short list, not "Add a rule"'s minutes box**: never expires (default), 1 hour, 8 hours,
  1 day, 7 days, 30 days. Two of the three places are pressed in the middle of reading something
  else. The server takes any number of minutes; a value not in the list is kept selectable and
  shown as it is ("Lasts 90 minutes"), so showing a request never changes what approving it grants.
- **E6. Refused, not dropped:** a lifetime on an agent-setting request (filing or approving; it
  creates no rule) and a lifetime with any answer but "Always allow" (no other answer files a rule).
  Precedent: the decision note (QA of 10-07) and finding 362, refuse rather than silently discard.
  A lifetime sent with a **rejection** is checked and then ignored: the note rides on both presses,
  and refusing a valid number on Reject would only make the form fail.
- **E7. De-duplication ignores the lifetime.** Two "Always allow" answers to the same question with
  different lifetimes still file one request (the first). The lifetime is not part of what the grant
  permits, and the approver chooses it at approval anyway.
- **E8. "Would allow" on a timed-out question (finding 338) gets no lifetime picker.** Its request
  asks for none; the approver's choice covers it like any other request.
- **E9. The ledger says it.** The submission entry ends "for N minutes" when a lifetime was asked
  for; the decision entry adds "; the rule expires <time>" when the granted rule expires; the
  rule-add entry already said "expires <time>". All three stay word for word as before when there is
  no lifetime, so no older entry or test reads differently.
- **E10. Fixed on sight:** `resolveRuleTtl` passed its input through `Number()`, so "Add a rule"
  accepted `ttlMinutes: true` as one minute and `[5]` as five. Both are refused now (a number or a
  numeric string only). It failed towards less access, and the dashboard never sends either, so it
  is recorded here and not given a finding number; the test is in the new file.

### 8.1 What D2-A is

1. **The shipped listing rule stays inside the project.** Pattern
   `^ls( -[a-zA-Z]{1,8})?( (?!/)(?!\.\.(?:/|$))(?!.*/\.\.(?:/|$))[A-Za-z0-9._/-]{1,200})?$`:
   one relative path, never absolute (the set has no `:`, `\` or `~` either) and with no `..`
   segment. Lookaheads, because a repeated segment group is a nested quantifier the
   pattern-safety check refuses (checked: `validateRulePattern` accepts it). `ls src`, `ls .git`,
   `ls -l -a` still allowed; `ls /etc`, `ls -la /root/.ssh`, `ls ../../..`, `ls src/../..` not.
   Its description changed with it, so its seed id did too.
2. **Installations made before it get it once** (policy document version 4, D3's precedent): a
   stored listing rule with the old id **and** the old pattern is replaced; one an Administrator
   changed or removed is left as it is.
3. **The folder a command runs in is judged as a path read**, before the command, through the
   same gate (`PartJudgement`, `policy-engine.ts`; `commandWorkingFolder`,
   `resource-extraction.ts`). The folder is the one the tool uses (finding 428's lesson): `exec`'s
   `workdir`, trimmed, relative to the **Gateway process's** folder and with no `~` expansion;
   the terminal's `cwd` on `open`, else the home folder for a relative or missing one.

**Decisions by precedent:**

- **E11. A folder no rule covers is refused, not asked.** One hook call carries one question; a
  question about the folder would let an unlisted command run unasked. Precedent: search results
  outside the rules are withheld, not asked about, because they have no approval path. The
  refusal tells the agent to leave the folder out or ask for a path rule. A forbid rule refuses
  the folder in every posture; monitor records an uncovered folder and lets it through.
- **E12. When the folder is refused, the command is recorded but not judged** (rule id
  `working-folder-refused`): recorded, because the engine's own principle is that every resource
  of a call is recorded before a verdict; not judged, because a judgement could record an "ask"
  for a question nobody was asked. (Found by the QA's review of the first version, which recorded
  only the folder.)
- **E13. The folder of a command sent to a paired node, or run in a sandbox, is judged as a host
  path.** Governance cannot tell from the call which host will run it; fail towards less access.
  Stated as a limit.
- **E14. No question for another agent's folder either.** Under decision (ii) a read inside
  another agent's folder is asked of its owner; as a working folder it is refused like any
  uncovered folder (E11's reason).
