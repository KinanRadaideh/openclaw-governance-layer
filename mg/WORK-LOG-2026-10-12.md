## 1. What the code did (read 2026-10-12)

- `policy.json` (one per organisation, `groups/<id>/policy.json`) is written in one place,
  `savePolicy` in `src/governance/policy-store.ts`, called by `updatePolicy` under the file lock,

- `loadPolicy` already defends the gate against a hand-edited file (core rules reasserted, bad

## 2. Decisions (by precedent; Kinan said decide and record)

- **E15. The expected fingerprint is a seal inside `policy.json`: an HMAC under the ledger key,
  with its own label, over the document as written.** Precedents: every ledger entry carries its
  own keyed seal (`ledgerEntrySealIsValid`), and the dashboard witness's receipt is an HMAC under
  the ledger key with its own label. Not a sidecar file: that is findings 209/210's "fact kept in
  two places" (a crash between the two writes would leave them disagreeing, a false alarm), while
  one atomic write keeps the seal and the document together. Not the chain itself: the policy is
  read on every tool call, many policy writes record no entry of their own (a stop, an expired-rule
  prune, an account deletion's cleanup), and an entry per write would put non-events in the record.
  An agent that edits the file without the key cannot make a valid seal, which is the protection
  the ledger has; one that reads the key can forge both, the limit `ledger-key.ts` already states,
  narrowed by supplying the key through the environment and closed only by option C (a separate
  operating-system account for tools).
- **E16. A write counter inside the seal catches an earlier copy put back.** Each write's seal
  covers a generation number one above the highest this process has seen. A validly sealed file
  older than one already seen is "an earlier copy put back" (an agent could keep a copy and restore
  it after an Administrator adds a denial). Remembered in memory: a copy put back and the Gateway
  restarted in the same step is not caught. Stated as a limit (the same evasion as reading the key:
  deliberate, and the agent's very next tool call catches it unless it also restarts the Gateway).
- **E17. A file with no seal raises the alert, including the first time after this upgrade.**
  Nothing without the key can tell a file written before seals from one whose seal was deleted, and
  accepting unsealed files silently would let anyone defeat the detection by deleting one field
  (the source is open). So every installation made before D9 shows **one** alert after the
  upgrade, worded to say that this is expected once, and Root acknowledges it. A fresh installation
  (no file yet) raises nothing.
- **E18. The changed file is used (it does not prevent), and is then sealed as found, so one change
  raises one alert.** Kinan's option says "does not prevent"; refusing the file would also let
  anything that can write it stop every agent. After the alert is recorded the store seals the file
  as found (under the lock, only if it is still the same file), so later loads, and later restarts,
  do not raise it again; a further edit raises a new one. In the same process the alert is also
  deduplicated by the file's fingerprint (T73's `reportedFindings`), which covers the moments before
  the reseal.
- **E19. A deleted file raises the alert while the Gateway runs.** With no file, governance loads
  the shipped baseline, so rules administrators added, stopped agents and per-agent settings stop
  applying: a deletion widens access. Detected when this process has already seen a policy file for
  the organisation; after a restart a missing file reads as a fresh installation (stated limit,
  E16's reasoning).
- **E20. No key, no check.** When the installation has no ledger key, nothing can be checked and
  no alert is raised; reading the key must not create one (findings 76 and 77: verification must
  not mint secrets). The key's own absence or replacement is the ledger's to report. A different
  key (restored from elsewhere) makes the seal fail: an alert, which is correct.
- **E21. An operator's own hand edit raises the alert too.** The store cannot tell a person from an
  agent. The alert's text names both, and Root's acknowledgement records which it was. The
  documents say that editing `policy.json` by hand is now visible.
- **E22. The alert is an integrity alert of the T73 kind**, written by the same labelled actor
  (`ledger-integrity`, reserved, holding no tier) through the same sealed writer, shown in the same
  banner to Administrators and Root, acknowledged by Root with a reason, and counted by the
  deployment report. It is **not** a chain alert: the chain is intact, so verification's "intact
  since N alerts" counts ledger alerts only. Installation-wide (`agentId` `-`) and outside the six
  policy kinds, so Users and Viewers do not see it (T73 and D12 precedent). The banner's title and
  hint are widened from "the audit ledger" to "governance's own records".
- **E23. The other governance files are not built now; recorded for Kinan.** Kinan's option names
  the policy file. The same gap exists for `users.json` (accounts and roles), the agent registry
  (`agents.json`) and `rule-requests.json`; the seal helper is written so it could be applied to
  them. Put to Kinan in `DOCUMENTATION-UPDATES.md` §9.

## 11. T86 D7, option A: what the code did, and the decisions

**What the code did (read 2026-10-12).** The gate's escalation (`policy-engine.ts`, the one
`requireApproval`) becomes an OpenClaw plugin approval (`plugin.approval.request`, carrying the
run's `turnSourceChannel`, `turnSourceTo`, …). Since T68 an escalation from a **dashboard prompt**
is governance-owned (`isGovernanceOwnedApprovalRequest`, by channel `governance` or the dashboard's
session-key shape): it is hidden from every Gateway connection (`approval-visibility.ts`,
`approval.ts`), not forwarded to chat channels or phones (`deliverRequest`), claimed on the
in-process bus by the governance route (`claimsAudience`), listed on the dashboard and answered
there by the accounts that manage the agent, the answer recorded with the account
(`governance.approval.answer`, and C15 for "Always allow"). An escalation from a **chat run**
(Discord, Telegram, Slack, WhatsApp, the Control UI's own chat) went to OpenClaw's approval
surfaces instead, where anyone with the channel or the Gateway credential could answer, and the
record said only that it was answered. Before asking, `requestPluginToolApproval` also refuses at
once when the run's channel cannot show approvals, and for every background run.

**Decisions (by precedent):**

- **E26. The gate marks its escalations** with `pluginId` `openclaw-governance`
  (`GOVERNANCE_APPROVAL_PLUGIN_ID`), and an approval carrying it is governance-owned whatever channel
  started the run, both live (`request.pluginId`) and stored (`presentation.pluginId`, which the store
  copies from the request). Every T68 rule then applies unchanged: hidden from Gateway connections,
  forwarded nowhere, claimed by the governance route, answered on the dashboard. A plugin that
  chose the same id would only make its own approvals stricter (answered on the dashboard).
- **E27. Who answers is T68's rule, unchanged**: an account that manages the agent (`canManageAgent`,
  same organisation), the foreign-folder rule (decision (ii)), refused while the agent is locked,
  recorded with the account. That is the gap D7 names, closed.
- **E28. The chat is told where to answer.** When a governance-owned escalation comes from a chat
  channel with an address (`turnSourceTo`), the governance route sends one message there through the
  Gateway's own `send` (the in-process route principal channel runtimes already use for their
  notices; best effort, once per approval by idempotency key): the agent is waiting for approval on
  the governance dashboard, what it asked, and that nobody answering means refused. **The Control
  UI's own chat (`webchat`) gets no notice**: `send` refuses it as internal, and writing into a
  session mid-run is not something an approval route should do; stated as a limit. Nothing is sent
  for a dashboard prompt (it is already on the dashboard).
- **E29. A user-started run's escalation no longer depends on its channel's own approval
  support**: the dashboard is the surface, so a Telegram run whose Telegram approvals are off is
  asked on the dashboard instead of refused at once. **Background runs (cron, heartbeat, memory
  dreaming) are still refused at once**: nobody is waiting on them, a question would stall the job
  for the whole approval window, and the refusal is already recorded. Unchanged.
- **E30. "When governance is on"** is always, except OpenClaw's own unconfigured test runs, which the
  gate exempts (`isUnconfiguredTestRun`) and which therefore raise no escalation.
- **E31. Other plugins' approvals and OpenClaw's own exec approvals are untouched**: they keep their
  chat buttons and the Control UI (the existing T68 test that a chat run's approval still reaches
  the Control UI stays, for a non-governance approval).
